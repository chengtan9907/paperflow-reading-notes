# Wizard: Manipulate Any World in Real Time via Agentic Control

> ★★★★☆ 推荐阅读 · 模型 openai-compatible/deepseek-v4-flash

🏷 关键词：world model · agentic control · video generation · character animation

## 一句话总结

Wizard 是一个 agentic 游戏世界模型：它在显式维护的游戏状态之上，用角色骨架几何与可编辑 3D 场景作为结构化中间代理来条件化视频扩散生成器，从而在未见过的场景、角色和动作上实现零样本泛化，并支持实时、细粒度的角色运动控制与状态感知的战斗交互。

## 摘要

> Recent advances in video world models have enabled the generation of increasingly realistic and interactive virtual environments, opening new possibilities for player-customizable gameplay. Agentic frameworks further advance this direction by decoupling explicit game logic and controllable world representations from visual generation. However, existing approaches support only simple game settings and predefined motion patterns, generalize poorly to unseen environments and characters, and offer limited real-time interactivity. In this paper, we introduce Wizard, an agentic game world model that enables real-time, precise control over character motions while generalizing zero-shot across novel scenes, characters, and actions. To achieve this, we construct a diverse dataset spanning 750 scenes and 178 characters, incorporating skeleton and geometry information as structured representations. We leverage these representations as intermediate proxies to condition a video generation model, together with an adaptive masking mechanism that improves alignment between the conditioning signals and generated video rollouts. Furthermore, we introduce an agentic framework that explicitly maintains and updates game states, allowing players to freely configure their virtual worlds and exercise fine-grained control over character motions while preserving visual quality and gameplay consistency. By combining agentic control with structured proxy-based generation, our framework unlocks new possibilities for player-driven game creation with real-time, generalizable, and mechanically consistent world simulation.

Q1: 这篇论文试图解决什么问题？

## 1. 论文瞄准的前沿问题

Wizard 处在“视频世界模型（video world model）→ 可交互游戏生成”这条研究脉络上。该脉络的基本设定是：给定视觉历史与当前动作，预测下一帧或下一段观测，从而把视频生成模型变成可被玩家操作的世界模拟器。论文在 Introduction 中把已有工作明确划分为几条路线，并逐条指出瓶颈：

1. **动作条件模型（action-conditioned）**：把鼠标、键盘输入直接作为条件。问题是动作空间通常被限制在预定义集合内，玩家无法执行训练时未定义的动作，控制灵活性受限。
2. **提示条件模型（prompt-conditioned）**：用文本或高层指令驱动生成。问题是模型倾向复现训练中出现过的运动与技能模式，对未见指令的遵循能力差，泛化性不足。
3. **agentic 框架 + 结构化代理**：维护显式世界状态，并把状态翻译成深度图、语义图、blockout、有向 3D 包围盒等代理去引导视频生成。这条路线提升了状态一致性与空间可控性，但论文指出其演示大多集中在基础运动上——车辆驾驶、角色位移（locomotion），对**关节化角色动作（articulated character actions）** 的支持非常有限。这是论文认定的核心空白。
4. **引擎路线（engine-based）**：用真实游戏引擎做结构化控制。问题是依赖预定义场景、需要额外处理管线，带来场景灵活性约束与交互延迟。

## 2. 核心问题的拆解

把上述空白翻译成可操作的技术问题，Wizard 需要同时回答四件事：

- **表示问题**：如何把“角色怎么动”这件事编码成视频生成器能稳定消费的条件？单纯的位置或包围盒不足以表达四肢关节的运动，必须引入骨架与几何。
- **泛化问题**：如何在用户上传的任意角色图、任意场景图上，零样本地完成“重建—绑定—驱动—渲染”，而不是依赖训练时见过的资产。
- **状态一致性问题**：游戏不只是画面，还有位置、姿态、血量、动作阶段、技能冷却等状态变量；这些变量必须被显式维护，并在多帧之间保持一致，否则会出现“画面里角色已经死了但状态还在攻击”的机制崩坏。
- **实时性问题**：视频扩散模型通常是多步去噪、长上下文注意力的，如何在保持画质的前提下把推理压到可交互的延迟与内存预算内。

## 3. 隐含假设

论文的方法隐含了几个较强的前提，值得在阅读时校准：

- 假设骨架 + 几何这类结构化代理与最终像素之间存在足够强的对应关系，因此可以通过掩码把条件“注入”到正确的位置；一旦角色外观与骨架差异很大（例如非人形、软体、多肢体），这个假设会承压。
- 假设运动库检索 + 重定向可以覆盖目标角色所需的动作集合。论文自己在结果部分承认，对运动库的依赖是主要限制之一，这意味着“任意世界、任意动作”的宣称有边界。
- 假设初始化阶段（重建场景、绑定骨架、构建目标运动集）可以控制在五分钟以内，从而不破坏“实时交互”的产品叙事；但这是初始化成本，不是每帧成本，二者需要区分。
- 假设显式世界状态足以刻画玩法一致性；对于需要复杂物理、多人同步、非战斗交互的场景，状态机的表达能力可能不足。

## 4. 评价难点

论文面对的评测困难也很典型：交互式世界模型缺少公认的定量基准。现有工作多以定性图例（给定参考图与代理，展示生成的 gameplay 帧）呈现，难以比较不同方法在长时一致性、动作保真度、指令遵循率上的差异。Wizard 的实验设置同样以定性评估为主，这会让“零样本泛化”和“实时”这两个核心宣称缺少可复核的数值支撑——这是阅读时应重点关注的证据缺口。

Q2: 有哪些相关研究？

## 1. 视频世界模型与交互式游戏生成

论文把自身定位在“从视觉历史与动作预测未来观测”的世界模型传统中，并明确指向游戏应用。Introduction 引用的 [1–5] 属于世界模型主干，[6–10] 属于把视频生成条件化到鼠标键盘输入、从而服务交互式与个性化 gameplay 的工作。这条线的共同假设是：视频生成模型可以充当渲染器，而控制信号决定世界如何演化。Wizard 与它们的差异在于，它不直接把低层输入喂给生成器，而是先经过一个显式的 agentic 状态层。

## 2. 动作条件 vs 提示条件

论文将已有控制范式分为两类并对立起来：动作条件模型 [11–13] 受限于预定义动作集；提示条件模型 [14–16] 依赖训练中见过的运动与技能模式，难以遵循未见指令。这一二分法基本覆盖了当前交互式视频生成的控制接口谱系，但也略显简化——现实中不少系统是混合接口。Wizard 的立场是：用结构化代理替代裸动作或裸文本，从而在保持控制精度的同时获得泛化。

## 3. Agentic 框架与结构化代理

这是与 Wizard 最直接相关的一条线。Code World Model [19] 与 Programmable World Model [21] 用 agent 生成的程序维护持久世界状态，并通过结构化代理引导视觉生成。论文对它们的批评是：主要强调状态一致性与实体级控制 [24, 25]，对细粒度角色动画探索不足。结构化代理的具体形态包括深度图 [18]、语义图 [19]、blockout [20]、有向 3D 包围盒 [21]。Wizard 的推进在于把代理从“实体级”细化到“关节级”：骨架 + 几何 + 语义肢体标签。

## 4. 引擎路线与 3D 场景操作

引擎类方法 [26, 27] 提供另一条结构化控制路径，但论文指出其依赖预定义场景与额外处理，带来场景灵活性与交互延迟的约束。与这条线相邻的是单图/视频的 3D 场景重建与编辑：Wizard 在场景侧使用 MoGe-2 做几何估计、OpenGL renderer 做可编辑 3D 几何渲染，并通过 world agent 把“Create stairs”这类自然语言指令翻译成 `def add_stairs()` 这样的可执行操作。这与程序化世界模型的思想同源，但作用在几何层而非逻辑层。

## 5. 角色动画与运动重定向

角色侧，Wizard 组合了多个现成视觉模型：Qwen3-VL 做结构分析、SAM2 做分割、TripoSG 做 mesh 重建、UniRig 做骨架绑定、Label Assign 做语义肢体标注。运动侧则依赖运动库（示例中出现 Gargoyle、Crucible Knight、Morgott、Red Wolf 等具名动作源），通过 VLM 评估运动风格与角色形态的匹配度做检索，再把源动作重定向到目标骨架。这条管线与图形学中的 motion retargeting 传统直接相连，区别在于它服务的是视频生成条件，而不是引擎内动画。

## 6. 视频扩散的实时化

生成侧，Wizard 以 Wan2.2-TI2V-5B [48] 为基座，冻结 VAE 与 UMT5 文本编码器 [49]，经过双向微调、因果适配与蒸馏，最终用 2 步去噪 + KV cache（保留 20 个近期 latent 帧与 1 个 persistent sink frame）实现有界内存的流式推理。这条线与视频扩散加速（少步蒸馏、因果注意力、流式 KV cache）的研究传统一致，是“实时”宣称的技术基础。

## 7. 数据与评测传统

论文构建了 750 场景、178 角色的数据集，包含 UE 仿真得到的对齐 proxy–video 对、脚本化 boss 战、角色与场景资产、骨架与 3D 关节位置等。评测上以定性图例为主（零样本泛化、开放式创意 gameplay），这与当前交互式世界模型领域缺少统一基准的现状一致，也意味着横向比较的可复核性有限。

Q3: 论文如何解决这个问题？

## 1. 总体架构

Wizard 由两大部分组成：一个 **agentic 框架**负责显式世界状态的维护与更新，一个 **视频生成器**负责把演化中的状态渲染成像素。二者之间通过**结构化视觉代理**衔接。整体流程分两段：初始化阶段（<5 分钟）与实时游玩阶段。

## 2. 初始化阶段：角色动画管线

角色侧的目标是：给定一张角色图，产出可被驱动、可被重定向的骨架与语义标签。管线为：

1. **结构分析**：Qwen3-VL 解析角色图像的整体结构；
2. **分割**：SAM2 做部件级分割；
3. **Mesh 重建**：TripoSG 从图像重建 3D mesh；
4. **骨架绑定**：UniRig 自动 rigging，得到骨架；
5. **语义肢体标注**：Label Assign 为关节与肢体链赋予语义标签（如左臂、右腿），使不同角色之间可以按身体部位做对应匹配。

运动侧则构建**目标专属运动集**：从一个运动库（示例含 Gargoyle、Crucible Knight、Morgott、Red Wolf 等来源）中，由 VLM 依据角色形态与预期运动风格评估匹配度，选出若干源动作；再通过 semantic limb label 做部位对应，把源动作**重定向**到目标骨架。最终得到包含 Walk、Run、Dodge、Attack 1、Attack 2、Hit reaction 等条目的运动集。这一步是“任意角色可被驱动”的关键，也是后面限制的来源。

## 3. 场景操作

场景侧走的是“单图 → 可编辑 3D 几何 → 视觉代理”的路径：用 MoGe-2 从场景图估计几何，交给 OpenGL renderer 渲染成可编辑的 3D 几何，再作为视觉代理供生成器消费。玩家可以通过自然语言指令修改场景，例如“Create stairs”，由 world agent 翻译成 `def add_stairs()` 这类可执行操作，从而在几何层真实地改变世界，而不是只在像素层“画”出楼梯。

## 4. 状态感知的战斗控制

框架维护一个**共享世界状态**，跟踪双方角色的位置、姿态（pose）、血量（HP）、动作阶段（action phase）与技能冷却（cooldown）。在此状态之上：

- **behavior planner** 依据当前状态选择行为；
- **rule-based controller** 把行为落实为具体运动选择；
- 玩家输入与 boss 决策共同驱动状态更新；
- 当血量归零时，控制器判定角色死亡、结束战斗并展示结果；框架允许灵活加入额外玩法规则。

这套设计的要点是：玩法一致性由状态机保证，而不是指望视频模型自己“记住”规则。

## 5. 生成器：结构化条件与自适应掩码

生成器以 Wan2.2-TI2V-5B 为基座，条件包括：几何与骨架代理、文本描述、最多两张角色外观参考图，以及历史帧。核心机制是**自适应掩码（adaptive masking）**：

- **空间掩码**从显式状态/代理中导出，作用在 token 网格上，限制哪些 token 可以关注哪些键；
- **时间注意力掩码**允许角色区域之外的 token 也去关注视频键；
- 掩码随显式状态动态更新，从而提升条件信号与生成 rollout 之间的对齐。

直观理解：骨架与几何告诉你“哪里应该有什么”，掩码把这个先验硬约束进注意力，减少条件与像素之间的错位。

## 6. 训练与实时推理

训练数据是 44,075 个 clip，每个 clip 配对几何+骨架条件、文本描述、最多两张角色参考。训练分三段：30K 步双向微调、10K 步因果适配、随后蒸馏；部署 500 步蒸馏后的 student EMA checkpoint。推理时用 2 步去噪，KV cache 保留 20 个近期 latent 帧加 1 个 persistent sink frame，实现连续、有界内存的流式生成。这是“实时交互”宣称的工程基础。

## 7. 关键设计权衡

- **用代理而非像素做条件**：提升可控性与泛化，但引入代理与像素之间的对齐误差。
- **用运动库而非生成式动作**：保证动作质量与物理合理性，但限制动作覆盖范围（论文自认的主要限制）。
- **用状态机而非端到端学习玩法**：保证机制一致性，但玩法规则需要人工设计。
- **用蒸馏换实时**：2 步去噪显著降低延迟，但可能牺牲画质与长时稳定性，论文未给出定量权衡曲线。

- **零样本泛化（Fig. 5）**：每个例子左侧是用户提供的场景或角色参考，右侧是配对的 agent 控制视觉代理与生成的 gameplay 帧。Fig. 5(a) 展示模型对未见场景、未见角色、未见运动的泛化。
- **开放式创意 gameplay（Fig. 6）**：展示玩家自定义世界与角色后的开放式玩法。

此外还展示了状态感知战斗控制的行为：血量归零时控制器判定死亡、结束战斗并展示结果，且框架允许灵活加入额外玩法规则（5.3 节的描述）。

## 4. 缺失的实验维度

从现有证据看，论文**没有**给出以下内容（属于证据缺口，不应臆测）：

- 与 baseline 的定量对比表（FVD、PSNR、动作误差、指令遵循率等）；
- 消融实验的数值结果（自适应掩码 vs 无掩码、骨架条件 vs 仅几何、蒸馏步数 vs 画质）；
- 实时性的定量指标（FPS、端到端延迟、显存占用曲线）；
- 用户研究或主观评分；
- 长时一致性（超过 4 秒窗口后的漂移）的量化评估。

因此，论文的说服力主要建立在定性图例与系统完整性上，而不是统计意义上的实验证据。这一点在判断其贡献强度时应予以权重。

Q5: 发现了什么实验现象？

## 1. 零样本泛化确实成立，但证据是定性的

Fig. 5(a) 的核心现象是：给定用户提供的场景图或角色图，agent 能控制视觉代理，并生成与代理一致的 gameplay 帧，覆盖未见过的场景、角色与运动。这是论文最强的能力宣称。但需要注意，这里的“泛化”是在**单例展示**层面成立的，缺少跨资产类别的成功率统计；对于与训练分布差异极大的角色（非人形、极端比例、透明/发光材质），泛化边界未被刻画。

## 2. 结构化代理与生成像素之间的对齐是核心张力

论文引入自适应掩码的动机，正是条件信号与生成 rollout 之间存在错位。空间掩码从显式状态导出、时间掩码允许角色外 token 关注视频键，说明作者观察到：如果不加约束，生成器会忽略骨架/几何条件或在错误位置渲染肢体。这暗示了一个反直觉现象——**条件越结构化，越需要显式的注意力路由来“强迫”模型使用它**，而不是简单拼接即可。论文未给出掩码开/关的定量对比，因此这一机制的实际增益大小未知。

## 3. 实时性来自工程组合而非单一技巧

实时交互依赖三件事叠加：因果适配（把双向注意力改成因果）、蒸馏（把多步压到 2 步）、有界 KV cache（20 帧 + 1 sink）。这是一个值得注意的系统性观察：单靠少步蒸馏不足以支撑流式交互，必须有内存有界的注意力设计。sink frame 的存在说明作者意识到纯滑窗 KV 会导致长时漂移，需要保留一个“锚点”帧来稳定外观。但 20 帧（约 0.67 秒 @30fps）的窗口相对于游戏时长仍然很短，长时一致性如何维持未被量化。

## 4. 战斗状态机的行为符合预期，但表达力有限

观测到的行为是：状态跟踪位置、姿态、血量、动作阶段、冷却；behavior planner 选行为，rule-based controller 选运动；血量归零则死亡、战斗结束、展示结果。这是一个可运行的闭环，说明“玩法一致性由状态机保证”的设计是有效的。但它也暴露了表达力边界：当前状态变量是为 1v1 类战斗设计的，对于多人、环境交互、非战斗玩法（解谜、平台跳跃、建造）是否够用，论文未讨论。

## 5. 运动库依赖是被明确承认的失败模式

结果部分的限制段落明确指出：对运动库的依赖使得某些动作难以覆盖。这是一个诚实的负结果。它的含义是：Wizard 的“任意动作”能力实际上是“运动库覆盖范围内的任意动作 + 重定向”，而不是真正的动作生成。当目标角色需要库中不存在的动作类型（例如四足奔跑、飞行、软体变形）时，系统会退化。

## 6. 资产规模与场景多样性

750 场景 / 178 角色的规模在学术工作中不算小，但相对于真实游戏资产库仍然有限。更重要的是，这些资产来自 UE 仿真与公开数据集，风格分布可能偏向写实奇幻（示例中的 Gargoyle、Crucible Knight、Morgott、Red Wolf 均带有明显的类魂系风格），对卡通、科幻、极简风格的覆盖未知。

## 7. 初始化成本与实时成本的区分

“<5 分钟初始化”包含场景重建、骨架绑定、运动检索与重定向，涉及 Qwen3-VL、SAM2、TripoSG、UniRig、MoGe-2 等多个外部模型。这些模型的误差会逐级累积（分割错 → mesh 错 → 骨架错 → 重定向错），论文未报告各阶段的失败率。实时性宣称只覆盖生成阶段，不覆盖初始化。

Q6: 有什么可以进一步探索的点？

## 1. 摆脱运动库依赖

最直接的方向是把“运动检索 + 重定向”替换为“运动生成”：用文本或高层意图直接合成骨架轨迹，再用物理约束或 diffusion prior 保证合理性。这样可以把动作覆盖从“库中已有”扩展到开放集合，也顺带解决非人形角色的运动适配问题。可行路线包括 motion diffusion、VLM 驱动的程序化动作合成、以及从视频中蒸馏运动先验。

## 2. 长时一致性与记忆机制

当前 KV cache 只保留 20 帧加 1 个 sink frame，理论上长时游玩会出现外观漂移与状态—像素错位。可以探索分层记忆（短期帧缓存 + 长期场景/角色嵌入）、稀疏全局注意力、以及显式的 3D 场景缓存回读。需要配套建立长时一致性指标（例如跨分钟级的角色身份保持度、场景几何稳定性）。

## 3. 更丰富的玩法与状态变量

把状态机从 1v1 战斗扩展到多人、环境交互、物理操作、解谜与建造。这要求状态表示从“位置/姿态/血量/冷却”扩展到包含物体状态、空间关系、任务进度等。也可以探索让 agent 自动生成玩法规则（程序化规则合成），而不是人工编写 rule-based controller。

## 4. 定量评测体系的建立

该领域急需基准：动作保真度（生成运动与代理骨架的关节误差）、指令遵循率、状态—像素一致性（例如血量归零时角色是否真的倒地）、长时漂移、以及交互延迟的标准化测量。Wizard 目前的定性评估是主要弱点，后续工作可以把这些指标做成可复现的 benchmark。

## 5. 代理与像素对齐的理论刻画

自适应掩码是一个启发式机制。可以进一步研究：条件信号的信息量、掩码粒度、注意力路由策略三者如何影响对齐误差；是否存在可证明的对齐上界；以及当代理本身有噪声（mesh 重建误差、骨架绑定误差）时，掩码是否会把错误放大。

## 6. 实时性的进一步压缩

2 步去噪 + 20 帧 KV 已是相当激进。可以探索 1 步生成、更紧凑的 latent 表示、以及面向游戏的专用解码器。同时需要给出画质—延迟的帕累托曲线，让使用者可以按场景选择工作点。

## 7. 与真实引擎的混合架构

把 Wizard 的生成器作为“神经渲染层”，与真实物理引擎或游戏逻辑引擎结合：引擎负责精确物理与规则，生成器负责视觉真实感与风格化。这可能比纯神经世界模型更适合需要严格机制一致性的商业游戏场景。

## 8. 多人同步与网络化

当前是单玩家 + boss 的设定。扩展到多人需要解决状态同步、视角一致性、以及每个玩家独立条件化生成的问题，这在架构上会带来显著挑战。

## 9. 鲁棒性与安全性

开放式用户输入（任意角色图、任意场景图、任意自然语言指令）带来分布外泛化与内容安全风险。可以研究输入校验、生成内容审核、以及对抗性输入的失效模式。

## 10. 数据集与资产管线的开放化

论文的数据集包含 UE 仿真、脚本化 boss 战、对齐 proxy–video 对，这类数据对社区有价值。开放数据与初始化管线（重建/绑定/重定向）可以降低复现门槛，也便于做跨方法的公平比较。

Q7: 总结一下论文的主要内容

## 一、论文要解决的问题

Wizard 瞄准的是“视频世界模型能否变成可玩的游戏”这一前沿问题。作者把已有工作归为四类并指出各自瓶颈：动作条件模型受限于预定义动作集；提示条件模型依赖训练中见过的运动模式，难以遵循未见指令；agentic 框架虽然维护显式世界状态并用深度图、语义图、blockout、3D 包围盒等结构化代理引导生成，但演示集中在车辆驾驶与角色位移等基础运动，对关节化角色动作支持不足；引擎路线则受限于预定义场景与额外处理带来的延迟。四类瓶颈交汇处的空白是：**细粒度角色控制、零样本泛化、实时交互、机制一致性四者无法同时满足**。

## 二、技术主线

Wizard 的解法是把“世界状态”与“视觉生成”彻底解耦，中间用结构化代理衔接。

**初始化阶段（<5 分钟）** 完成三件事。角色侧：Qwen3-VL 做结构分析、SAM2 做分割、TripoSG 重建 mesh、UniRig 绑定骨架、Label Assign 赋予语义肢体标签，使不同角色可以按身体部位对应。运动侧：从运动库中由 VLM 依据角色形态与运动风格检索源动作，再通过语义标签重定向到目标骨架，形成包含 Walk、Run、Dodge、Attack、Hit reaction 等的目标专属运动集。场景侧：MoGe-2 估计几何，OpenGL renderer 渲染为可编辑 3D 几何，world agent 把“Create stairs”这类指令翻译成 `def add_stairs()` 这样的可执行操作。

**实时游玩阶段**：一个共享世界状态跟踪双方角色的位置、姿态、血量、动作阶段与技能冷却；behavior planner 依据状态选行为，rule-based controller 落实为具体运动；玩家输入与 boss 决策共同驱动状态更新；血量归零则判定死亡、结束战斗。视频生成器（以 Wan2.2-TI2V-5B 为基座，冻结 VAE 与 UMT5）消费几何+骨架代理、文本描述、最多两张角色参考图与历史帧，渲染出对应的 gameplay 画面。

**自适应掩码**是连接代理与像素的关键机制：空间掩码从显式状态导出，作用在 token 网格上限制注意力路由；时间注意力掩码允许角色区域之外的 token 关注视频键；掩码随状态动态更新，以改善条件信号与生成 rollout 的对齐。

**训练与推理**：44,075 个 clip，每个 clip 配对几何+骨架条件、文本描述、最多两张参考图；30K 步双向微调 → 10K 步因果适配 → 蒸馏；部署 500 步蒸馏后的 student EMA。推理用 2 步去噪，KV cache 保留 20 个近期 latent 帧加 1 个 persistent sink frame，实现有界内存的流式生成。

## 四、主要贡献与边界

贡献可以概括为四点：一是把 agentic 世界状态与关节级结构化代理（骨架+几何+语义标签）结合，实现细粒度角色控制；二是通过“单图重建—绑定—重定向”的管线实现跨场景、跨角色、跨动作的零样本泛化；三是引入自适应掩码改善条件与生成的对齐；四是通过因果适配、蒸馏与有界 KV cache 实现实时流式交互。

边界同样清晰：运动库依赖限制了动作覆盖范围（作者明确承认）；评测以定性为主，缺少可复核的定量证据；初始化阶段涉及多个外部模型，误差会逐级累积；4 秒窗口与 20 帧 KV 对长时一致性的支撑能力未被量化；玩法状态机目前主要覆盖 1v1 类战斗。
