# ReuF2F: Benchmarking Coding Agents on Formalized Undergraduate Research Problems

> ★★★★☆ 推荐阅读 · 模型 openai-compatible/deepseek-v4-flash

🏷 关键词：formal mathematics · lean 4 · open problems · coding agents

## 一句话总结

本文提出 REUF2F——一个包含 244 个来自本科生科研项目（REU）且已形式化为 Lean 4 的开放数学问题基准，配套统一的 coding-agent 评估框架（Leanimum-agent），并发现当前最强模型 Gemini 4 Argon 也仅能在约 40% 的问题上给出被接受的证明或反驳，表明形式化开放数学问题对现代智能体仍具显著挑战。

## 摘要

> 随着 AI 系统开始解决开放研究问题，可靠的验证变得日益重要。形式化数学（如 Lean 4）提供了可信的推理框架，能让智能体在数学探索中产出机器可检查的证明。然而，现有形式化数学基准往往集中于已知结果或少数著名开放问题，一旦解决方案被发现并广泛传播，评估可靠性就会下降；同时，现有评估协议也未必符合现代 coding agent 的工作方式。为此，作者引入 REUF2F：一个包含 244 个形式化开放问题的 Lean 4 基准，这些问题源自本科生研究经历（REU），覆盖多个数学子领域的入门级开放研究问题。这些不太知名的问题往往受关注较少、可能长期未解，更适合作为端到端开放问题求解能力的 held-out 评估。他们采用标准 coding-agent 评估设置，将每个问题及其逻辑否定放入 Docker 容器中的 Lean 项目，并基于 mini-SWE-agent 构建了统一的评估 harness——Leanimum-agent，以支持模型间的公平比较。评估结果显示，即使性能最好的模型也只能解决约 40% 的问题，说明在形式化开放研究问题上仍有很大改进空间。

Q1: 这篇论文试图解决什么问题？

这篇论文试图解决的核心问题是：如何在大模型（LLM）能力快速提升、甚至开始解决长期未解的开放数学问题的背景下，构建一个可靠、长期有效、且与现代 coding agent 工作方式对齐的评估基准。具体而言，论文指出现有形式化数学基准存在三个关键缺陷：第一，很多基准聚焦于已知结果或少数著名开放问题，这些问题的答案一旦被公开发表或在网上广泛传播，后续评估就可能被数据污染，智能体可以通过检索直接获取解决方案，从而丧失对真实开放探索能力的测量效度；第二，已有评估协议往往以“填空式”的形式要求智能体补全单独的 theorem 或 proof hole，这与现代 coding agent 在完整项目环境中读写代码、运行构建、迭代调试的实际工作流不符；第三，开放问题本身的真值未定，正确的回应既可能是证明也可能是反驳，若评估只接受其中一种，就会把数学上的“无法判定”误判为智能体能力不足。此外，形式化过程中存在元编程、非平凡公理、计算不可判定性等复杂因素，如何确保最终提交的证明或反驳确实经过可信内核的验证，也是评估设计的一大难题。因此，论文希望提供一个能同时满足以下条件的基准：问题足够新颖和偏远以降低污染风险；问题已经完整形式化，无需智能体处理自然语言到形式语言的转换；评估协议允许证明或反驳任一方向；验证流程由可信的 Lean 内核与辅助检查器双重把关；并通过统一 harness 实现对不同模型的公平对比。最终目标是让 REUF2F 成为跟踪 coding agent 在“全新数学发现”这一终极任务上进展的可靠标尺。

Q2: 有哪些相关研究？

相关工作可分为几个脉络。第一，AI 数学推理与 RLVR（可验证奖励的强化学习）：论文引用了 Guo et al. (2025)、Yue et al. (2025) 等研究表明数学和代码问题“构造难、验证易”的特点使其非常适合 RLVR；近年来进展从竞赛题扩展到解决长期开放问题，例如对单位距离猜想的反证（OpenAI, 2026c）、六维球面上的复结构（Alpöge, 2026）、OpenAI 报告的十项数学与理论计算机进展（OpenAI, 2026d）以及 Navier-Stokes 有限时间爆破结果（OpenAI, 2026a）。这些工作既展示了模型潜力，也凸显了对可靠验证的需求。第二，形式化数学与证明助手：Lean 4 通过 Curry-Howard 对应将数学命题表示为类型、证明表示为项，内核可核验正确性（Moura & Ullrich, 2021）；Mathlib 为形式化提供了丰富库支持。已有基准如 miniF2F、ProofNet、 PutnamBench、Firsching et al. (2026)、Tsoukalas et al. (2024) 等包含 known results、竞赛题或少量论文中的 open problems，但多为单个定理填空式任务，且对“一旦解决便失去评估价值”的长期可持续性考虑不足。第三，coding-agent 基准与评估框架：SWE-bench、ProgramBench（Yang et al., 2026）等为代码智能体提供了在真实仓库中完成修改、运行测试、生成补丁的评测范式；论文指出这些范式提供了 harness 一致性和环境隔离的成熟方案，可直接迁移到形式定理证明任务中。第四，自动形式化与证明搜索：相关工具如 nanoda 等用于独立核对证明项，Lean 的 metaprogramming 和 code execution 能力使得正确性验证不能仅仅依赖内核——必须同时考虑不健全的策略或外部调用带来的风险。本文与这些工作的区别在于：它专门面向“开放研究问题”这一尚未被系统覆盖的类别，并首次将 coding-agent 式评测协议应用于 Lean 4 的开放问题证明/反驳任务。

Q3: 论文如何解决这个问题？

论文通过构建 REUF2F 基准和配套的评估框架来解决上述问题，具体包含五个部分：
1. 数据采集与问题选取：从本科生研究经历（REU）项目中收集了 244 个开放的数学猜想。这些问题的特点是位于“入门级开放问题”层次，覆盖组合学、图论、代数、分析等多个子领域；它们往往不如菲尔兹奖级问题著名，受关注度低，因此预期会在较长时间内保持未解决状态，适合作为 held-out 评估。
2. 形式化：由专家将这些开放问题完整形式化为 Lean 4 语句，每个问题放置在一个独立的 Lean 项目中，项目仅包含该问题及其逻辑否定（negation），并依赖 Lean 和 Mathlib v4.34.0。形式化过程中没有使用 sorry 占位符作为待填写的 proof hole，而是要求智能体从零开始构造证明或反驳。
3. 任务构造与容器化：按照 coding-agent 标准评估设置，每个问题与其否定形式分别放入 Docker 容器中的 Lean 项目，形成 488 个独立任务实例（244×2）。智能体可以自由读取项目文件、编译、运行命令、生成补丁；评估环境同样使用 Docker 隔离，保证环境一致性和安全性。
4. 统一评估 harness：构建了 Leanimum-agent，基于 mini-SWE-agent 开发，为所有模型提供相同的工具接口、上下文管理和补丁提交流程，以消除不同 agent 实现差异带来的不公平性。每个尝试上限为 1000 代理步、6 小时墙钟时间，单个 shell 命令超时 1200 秒；临近结束时 agent 会收到提醒以完成并提交补丁。提交的补丁在一个全新的评估容器中运行，超时为 6 小时。
5. 双重验证（Comparator）：所有提交必须通过 Comparator 验证。Comparator 首先使用官方 Lean 内核检查补丁是否成功构建并证明了目标定理或其否定；其次使用独立检查器 nanoda 再次验证，以防止依赖不可信的自定义策略、宏或非平凡公理（如 unsafe axioms）绕过内核。只有当任一方向的证明被两个检查器同时接受时才计为通过。这种设计确保了“被验证的结果”不仅是语法上可编译的，而且是数学上可信的。

Q4: 论文做了哪些实验？

论文在 REUF2F 上进行了一系列实验，分为三部分：
1. 前沿模型全基准评估：使用 Leanimum-agent 评估了多个当前前沿模型，涵盖完整的 488 个任务实例（244 个问题 × 证明/反驳两个方向）。每配置对每个问题安排两次独立尝试，报告 pass@1（被接受尝试数除以 488）和 pass@2（两次尝试中至少一次成功的比例）。实验配置固定为 Lean 和 Mathlib v4.34.0，agent 容器和评估容器使用相同硬件（20 CPU 核心、60GB RAM）并允许互联网访问；不设金钱成本上限，只设步骤和时间上限。
2. 测试时推理努力（test-time reasoning effort）的规模效应：研究模型性能如何随推理预算变化，可能是通过增加采样步数、思考时间或重试次数来控制，论文摘要提到“study how their performance scales with test-time reasoning effort”，但具体曲线需要查阅正文。
3. 多模型对比与领域/解决类型分析：在更多模型上比较性能，并按数学领域（如组合、代数、分析等）和解决类型（证明 vs 反驳）进行细分，考察 agent 在不同数学结构上的表现是否存在显著差异。
最终结果显示最佳模型 Gemini 4 Argon 达到 pass@1 42.42%、pass@2 44.67%，是当前最高分数。
所有评估均通过同一 harness 进行，并采用 1000 步、6 小时等宽松限制，以期逼近模型的能力上限。

Q5: 发现了什么实验现象？

根据论文报告的关键实验现象：
1. 总体解决率仍偏低：最先进的 Gemini 4 Argon 也仅解决约 42% 的问题（pass@1 42.42%，pass@2 44.67%），意味着超过一半的开放问题在当前预算下无法被任一模型解决。即使允许两次尝试，增益也只有约 2 个百分点，说明单次成功率低且二次尝试带来的边际收益有限。
2. 存在明显的提升空间：论文认为结果“留下 substantial room for improvement”，表明在开放数学研究任务上，前沿模型距离人类研究生水平仍有距离。
3. 领域间差异（合理推断）：论文在结果部分提到“arguments involving intuitive reasoning, explicit constructions, or extensive case analyses may be concise on paper but laborious to formalize in Lean”，暗示不同数学论证类型的可形式化程度差异大；有些论证在纸上简短但形式化繁琐，而代数/分析类论证可能更易机械化。这意味着领域维度上的成功率可能有分层现象，但具体数字需查正文。
4. 测试时推理努力的规模效应（未给出具体数值）：论文专门考察了性能随测试时推理努力的变化，但摘要中未披露详细趋势；从结论推断，增加计算投入可能能提高解决率，但收益可能递减。
5. 非平凡公理与不可判定性问题：论文指出某些问题在允许的公理基础下是不可判定的，这样的问题无论如何无法在协议下解决，这意味着“未解决”并不等同于“智能体能力不足”，而可能是任务本身的性质。这为解释失败提供了一个重要混淆因素。
6. 形式化忠实性风险：尽管形式化由专家完成并经过独立 AI辅助检查，但仍存在形式化与原始数学猜想语义不完全对齐的可能，从而影响评估的外部效度。

Q6: 有什么可以进一步探索的点？

基于论文提出的基准和初步结果，可以进一步探索的方向包括：
1. 提升 agent 能力：开发更强的搜索策略、更好的证明状态表示、结合外部求解器（如 ATP/SMT）、利用证明树引导回溯，或针对 Lean 的 metaprogramming 能力进行强化学习，以突破当前 40% 的解决率瓶颈。
2. 扩展基准范围：将 REUF2F 扩展到更多 REU 项目和研究生水平问题，覆盖更广泛的数学子领域，并定期补充新问题以维持 held-out 性质；也可以加入其他证明助手（如 Coq、Isabelle）的对应版本，以考察框架可移植性。
3. 处理数据污染与长期效用：开发自动检测解决方案是否已在线上传播的机制，或采用动态生成/合成新问题的方式，延长基准寿命。
4. 形式化自动化的研究：许多开放问题的“纸上证明”简短但形式化繁琐，自动形式化工具（如基于 LLM 的 autoformalization）若能逐步自动化这层转换，将大幅降低 agent 进入数学研究的门槛。
5. 验证协议本身的深化：研究如何应对非平凡公理和元编程带来的信任漏洞，开发更全面的独立验证链；探索在 Lean 内嵌入可判定性证明，以识别哪些问题在给定公理下不可判定，从而在报告结果时区分“未解”与“不可解”。
6. 评测协议的更细粒度分析：不仅看最终是否通过，还要记录 agent 的中间步骤、提交补丁的修改类型、尝试次数、失败模式（如编译错误、超时、逻辑错误），以定位能力的系统短板。
7. 与人类数学工作流的整合：将 REUF2F 用作“数学助手”的持续评估平台，追踪模型从提出猜想、形式化、到证明/反驳的完整研究闭环。

Q7: 总结一下论文的主要内容

论文针对 AI 在数学研究中快速进步所带来的评估难题，提出并构建了 REUF2F 基准。
论证主线：作者观察到，大语言模型在数学和代码任务上已通过 RLVR 等范式取得显著进展，从解决竞赛题扩展到攻克长期开放问题（如单位距离猜想反例、六维球面复结构、Navier-Stokes 有限时间爆破等）。然而，这些突破也带来了评估危机：自然语言证明的正确性难以大规模自动验证；而形式化证明（Lean 4）虽然能提供机器可检查的证明，但已有基准要么聚焦已知结果（容易被训练数据覆盖），要么只包含少数著名开放问题（一经解决即失效），且评估协议多采用填空式补全，不符合现代 coding agent 在真实代码仓库中迭代工作的习惯。因此需要一个“不容易被污染、可长期使用、与现代 agent 工作流对齐”的开放问题评测基准。
技术主线：作者从 REU 项目中精心选取 244 个开放猜想，由专家将其形式化为 Lean 4 语句，每个问题与其否定放入独立 Lean 项目。他们设计了统一的评估 harness Leanimum-agent（基于 mini-SWE-agent），提供 Docker 容器隔离、工具调用、补丁生成与自动验证全流程。验证端采用 Comparator：同时依赖 Lean 官方内核与独立检查器 nanoda，确保提交的证明或反驳不仅编译通过，而且不存在依赖不可信公理或被元编程规避核验的风险。评估协议允许任一方向（证明或反驳）被接受，体现了对开放问题“真值未知”的认识。
实验主线：在统一的宽松预算（1000 步、6 小时、无金钱限制）下评估了多个前沿模型。结果显示最佳模型 Gemini 4 Argon 的 pass@1 为 42.42%，pass@2 为 44.67%，即约 60% 的开放问题在给定预算下仍未被解决。论文还分析了测试时推理努力的规模效应、跨领域和跨解决类型（证明 vs 反驳）的表现差异，并讨论了形式化忠实性和不可判定性对结果解读的影响。
结论：REUF2F 可以作为跟踪 coding agent 在开放数学研究上能否产生新的、经过验证的结果的可复现基础。当前模型表现虽然有限，但已展示出一定的端到端形式化研究能力，且留有巨大提升空间。
