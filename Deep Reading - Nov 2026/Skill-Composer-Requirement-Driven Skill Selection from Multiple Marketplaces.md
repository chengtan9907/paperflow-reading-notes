# Skill-Composer: Requirement-Driven Skill Selection from Multiple Marketplaces

> ★★★★☆ 推荐阅读 · 模型 openai-compatible/deepseek-v4-flash

🏷 关键词：agent skills · skill marketplace · skill selection · set cover

## 一句话总结

论文主张把 Agent 技能获取从“按查询相关性给单个技能排序”重构为“面向任务需求的集合选择”，并提出 Skill-Composer：把用户需求拆成原子需求点、跨多个技能市场检索并合并候选、分解每个候选技能的能力、渐进式剔除重叠技能，最终产出非冗余且尽可能覆盖全部所需能力的技能组合，并显式报告未被覆盖的能力缺口。

## 摘要

> 说明：所给证据来自双栏 PDF 的摘要抽取，左右栏文本交错，出现明显断行与串行（例如 “2026 actually faces”“Nov acquisition” 这类错位片段）。以下为按语义还原的清洁版摘要，凡涉及具体措辞均以原文为准。
> （1）背景：Agent skill 已经成为智能体复用专门化能力的主要载体，但公开的技能市场（skill marketplace）在接口层面只提供“单品检索”：用户给出一个 query，市场用关键词或向量相似度匹配，返回一串按相关性或热度排序的单个技能。
> （2）问题：这种接口回答不了开发者真正面对的问题——为了完成一个任务，究竟应该安装哪一组技能，才能让任务被完整覆盖？该局限不来自检索质量本身，而来自接口的语义单位（单个技能 + 单个查询）。它体现在两个层面：一是检索到的技能是否覆盖了用户的完整需求；二是候选之间是否互相冗余。
> （3）机制解释：查询相关性不等于需求对齐。一个 query 只是几个关键词，而一个任务携带若干子需求，其中一部分被明说、一部分是隐含的；query-relevance 分数完全不表达“这个技能到底满足了哪几条子需求”。同时，候选技能之间是互相冗余的：市场里存在大量能力重叠的技能，而由于每个候选都是被独立打分的，这种重叠不会被察觉，于是列表顶部会被近似重复项占满，而任务真正需要的能力反而无人覆盖。
> （4）实证支撑（论文引用）：已有研究表明，任何人从这些市场下载的技能往往并不能带来显著提升（原文引用编号 [6]，需回原文核对具体文献与实验条件）。
> （5）主张：因此技能获取应当从 ranking 重构成 set selection。
> （6）方法：提出 Skill-Composer，一个 agent-native 框架，为用户需求挑选一个非冗余的技能 bundle，目标是覆盖所有可获得的必需能力，并报告任何缺口。具体地，它把用户需求澄清为原子需求点（atomic requirement points），跨碎片化的多个市场检索并合并候选技能，对每个候选技能做能力分解（capability decomposition），再渐进式地丢弃重叠者，使每一个被保留的技能提供互不相同的能力。
> （7）论文还探讨了 ClawHub 的公共 API 如何支撑这一任务，并给出 Figure 1 的结果（具体数值未在证据中给出，需回原文核对）。此外 References 片段中保留了一句对缺口归因的自省：“whether a reported gap reflects a real hole in the ecosystem or a weakness in our own decomposition”，说明论文把“缺口报告的可信度”当作需要单独论证的问题。

一、接口层面的错配（摘要明确支持）
现有技能市场的检索原语是“query → 单个技能的有序列表”，排序依据是关键词匹配、向量相似度或流行度。这意味着接口的语义单位是“单品”，而开发者的决策单位是“一组”。论文指出，这个错配不能靠“把检索做得更好”解决——它不来自检索质量，而来自接口的形状。

二、真实问题：应该安装哪一组技能（摘要明确支持）
开发者面对的问题可以形式化地读成一个覆盖问题：给定任务 T 的一组必需能力 C(T)，从市场集合 M 中选出一个子集 S，使得 S 的联合能力覆盖 C(T)，同时 S 内部尽量不冗余。这是一个集合选择（set selection）/覆盖（coverage）问题，而非排序问题。

三、两层失效（摘要明确支持，是论文的核心诊断）
1）覆盖层：检索结果不一定覆盖完整需求。原因是 query relevance ≠ requirement alignment——query 是几个关键词，任务是若干子需求，其中既有显式陈述的，也有隐含未说的；相关性分数不表达“该技能满足了哪几条子需求”。
2）冗余层：候选之间功能重叠。市场里同一能力被大量技能重复实现；因为每个候选是独立打分的，重叠不可见，于是 top-k 被近似重复项占满，而任务真正需要的能力落空。
这两层是耦合的：冗余挤占名额，直接导致覆盖缺口。

四、碎片化（摘要明确支持，但细节不足）
论文强调“跨碎片化的多个市场（fragmented marketplaces）检索并合并候选”，说明单一市场无法覆盖全部所需能力，且同一技能/等价能力可能分布在不同市场，需要合并与去重。证据中提到 ClawHub 的公共 API，合理推断 ClawHub 是论文实际使用或重点分析的一个市场/来源。

五、现有实践为何不奏效（摘要明确支持，引用层面）
论文引用已有研究指出：从这些市场下载的技能往往没有带来显著提升（原文 [6]）。这一条是论文用来论证“当前的选择方式本身有问题”的外部证据；具体文献、任务与显著性判定需回原文核对，本报告无法确认其适用范围。

六、缺口归因问题（References 片段支持，是论文自觉的元问题）
片段中出现“whether a reported gap reflects a real hole in the ecosystem or a weakness in our own decomposition”，说明论文意识到：一旦框架开始“报告缺口”，就必须区分“生态里真的没有这个能力”与“我们自己的能力分解做错了”。这是一个容易被忽略但会直接决定 gap report 可信度的评价难题。

一、总体形态（摘要明确支持）
输入：一个自然语言任务/需求 + 若干技能市场（至少包含 ClawHub）。
输出：一个技能 bundle（非冗余的技能集合）+ 一份缺口报告（哪些必需能力没有被任何已选/候选技能覆盖）。
定位：agent-native 框架，即面向智能体运行时而设计，而不是给人看的搜索页面。

二、四阶段流程
阶段 1：需求澄清 → 原子需求点（atomic requirement points）
- 摘要明确：把用户需求澄清为原子需求点。
- 关键点在于“原子”：需求要被拆到不可再分、可被单个技能满足的粒度，否则覆盖判定无法做。
- 推断：这一步很可能由 LLM 完成，输出是一组需求点列表，并可能区分显式需求与隐式需求（摘要明确提到任务含“some stated and some implicit”，因此推断框架需要显式建模隐含需求）。
- 失败模式：拆分粒度过粗→少量技能即“全覆盖”，掩盖真实缺口；过细→缺口爆炸、大量不可满足项；隐含需求误推断→假覆盖或假缺口。

阶段 2：跨市场检索与合并（retrieve and merge across fragmented marketplaces）
- 摘要明确：跨碎片化市场检索并合并候选技能。
- 推断：以每个原子需求点为单位发起检索（而不是用原始 query 检索一次），再对多市场返回结果做合并与跨市场去重（识别同一技能的多市场副本或镜像）。
- 失败模式：跨市场等价性判定错误会导致“以为是两个技能、其实是一个”，或反之；各市场检索接口能力不一致（证据中提到探索 ClawHub 公共 API 的支持程度，说明接口能力本身是一个工程约束）。

阶段 3：候选能力分解（decompose each candidate's capabilities）
- 摘要明确：分解每个候选技能的能力。
- 这是把“技能”映射到“能力集合”的关键一步，也是全流程的语义中枢：只有技能侧与需求侧都被表示为能力集合，覆盖与重叠才可计算。
- 推断：能力可能来自技能描述/文档/示例的结构化抽取，输出能力集合（甚至能力标签），并可能要求能力表述与需求点使用同一“词汇表”以便匹配。
- 失败模式：这是全系统最大的单点误差源。技能描述本身可能夸大、含糊、遗漏隐式能力；分解器可能把“调用某 API”误当能力，或把复合能力拆得过细。论文在 References 片段中自省“缺口到底是生态真空还是我们分解的弱点”，正对应这一风险。

阶段 4：渐进式剔除重叠（progressively discard overlapping skills）
- 摘要明确：渐进式丢弃重叠者，使每个被保留的技能提供不同的能力。
- “渐进式/progressively”+“丢弃”这一措辞强烈提示是贪心式迭代选择：按某种优先级（覆盖新增能力最多、或单位冗余最小）逐个纳入技能，一旦某个候选带来的新增能力为空或低于阈值就丢弃。
- 与贪心集合覆盖（greedy set cover）在形式上同构（推断）。若确实如此，则天然继承其 (1-1/e) 近似保证，但也继承其对重叠结构的短视。
- 失败模式：贪心顺序敏感；两个各自不完整的技能组合起来才覆盖某能力的情况会被误判为缺口；没有回溯机制时早期错误无法修正。

阶段 5（隐含但关键）：缺口报告与归因
- 摘要明确：目标是覆盖所有可获得的能力，并报告任何缺口。
- 论文显然把“gap report”当作一等输出，并且意识到需要区分“生态真空”与“分解误差”（References 片段）。
- 推断：可能设计了某种验证/复核环节（例如对报告出的缺口做二次检索或人工核验），否则无法支撑这一区分；具体机制必须回原文确认。

一、论证主线
论文从一个接口观察出发：Agent skill 已成为智能体复用专门化能力的主要载体，而公开技能市场提供的检索原语是“给一个 query，返回一串按相关性或热度排序的单个技能”。作者认为，这个接口回答不了开发者真正的决策问题——为了完成一个任务，应该安装哪一组技能。
随后论文把这一失败拆成两个层面。第一层是覆盖：检索到的技能是否覆盖了用户的完整需求。第二层是冗余：候选之间是否互相重叠。二者由同一个机制驱动：query relevance 不等于 requirement alignment。query 只是几个关键词，而任务携带多条子需求，有的被明说、有的是隐含的；相关性分数不表达“这个技能满足了哪几条子需求”。又因为每个候选是独立打分的，候选间的能力重叠不会被察觉，于是列表顶部被近似重复项填满，任务真正需要的能力反而无人覆盖。
论文用一条外部证据加固这一诊断：已有研究表明，从这些市场下载的技能往往没有带来显著提升（原文 [6]，需核对）。这条证据与冗余诊断互相咬合——装一堆高度重叠的技能，边际收益自然趋零。由此得出核心主张：技能获取应当从 ranking 重构为 set selection。

二、技术主线
Skill-Composer 是一个 agent-native 框架，输出不是列表而是 bundle 加缺口报告。流程分四步（摘要明确）：
1）需求澄清：把用户需求拆解为原子需求点，使其可被逐个判定满足；摘要特别指出任务含显式与隐含子需求，暗示框架需要处理隐含需求。
2）跨市场检索与合并：面向碎片化的多个技能市场检索候选并合并，解决单一市场覆盖不全与同一技能在多市场重复出现的问题；证据提到 ClawHub 公共 API 的支撑能力。
3）能力分解：把每个候选技能分解为能力集合——这是全系统的语义中枢，只有技能侧与需求侧都被表示为能力集合，覆盖与重叠才可计算。
4）渐进式剔除重叠：迭代地丢弃重叠技能，使每个被保留的技能提供互不相同的能力。这一形态与贪心集合覆盖同构（推断），因而天然继承“先选增益最大者”的直觉，也继承其顺序敏感与短视。
最终产出满足“覆盖全部可获得能力”的非冗余组合，并把无法覆盖的部分作为缺口显式报告。缺口报告是本文相对排序接口的结构性增量：排序接口在表达上无法说出“没有东西能满足你”。
