# APPSim-Bench: Bridging Real-world Apps and Reproducible Evaluation for Mobile GUI Agents

> ★★★★☆ 推荐阅读 · 模型 openai-compatible/deepseek-v4-flash

🏷 关键词：mobile gui agent · agent benchmark · reproducible evaluation · simulated apps

## 一句话总结

论文提出 AppSim-Bench：用「可控模拟 App + 确定性结果验证」替代简化环境与真实商业 App 之间的二选一，在 17 个中英文高频 App 的 557 个任务上实现可复现的移动 GUI Agent 评测，并发现 19 个受测 agent 中最佳者仅完成 50.27% 任务、28.55% 任务无任何 agent 能解。

## 摘要

> Mobile GUI agents can execute tasks from natural-language instructions, but their evaluation remains difficult to make both realistic and reproducible. Existing benchmarks typically trade off these goals: simplified apps lack real-world mobile complexity, whereas live commercial apps introduce uncontrolled variation from recommendations, advertisements, accounts, and changing content. We propose AppSim-Bench, which addresses this trade-off through controllable simulated apps that preserve task-relevant interaction logic while supporting deterministic evaluation. Built through a coding-agent-assisted and human-verified workflow, it contains 557 tasks across 17 high-frequency Chinese and English apps. Its controllable backend data and outcome-based verification remove major sources of environmental stochasticity, enabling reproducible cross-model comparison. Evaluating 19 GUI agents, spanning general-purpose and GUI-specialized systems, we find that autonomous mobile execution remains far from solved. The best model completes only 50.27% of tasks, and 28.55% of tasks are not solved by any agent. Further analysis shows that failures concentrate in longer workflows, numerical reasoning tasks, and inefficient trajectories marked by high action overhead and budget exhaustion. Our project is available at https://github.com/Acrab-Agentic-Labs/AppSim.

Q1: 这篇论文试图解决什么问题？

论文试图解决的问题是移动 GUI Agent 评测中的「真实性—可复现性」两难，以及由此派生的跨模型比较不可信问题。

1) 问题的定位（论文明确支持）。摘要与 Introduction 片段指出：移动 GUI Agent 可以执行自然语言指令，但评测要同时做到真实与可复现很困难。现有基准「典型地在两个目标之间取舍」：一类是简化 App，它牺牲了真实移动端复杂度；另一类是真实商业 App，它引入了推荐、广告、账号状态、内容不断变化等不可控变异。论文并明确引用了既有工作（Zhang et al., 2024a）已经指出可复现性问题，但认为「一个通用且高效的解决方案仍然缺失」。这意味着本文的定位不是首次提出可复现性议题，而是填补「通用且高效方案」的空缺。

2) 为什么这是真问题（合理推断，结合常识与片段）。GUI Agent 评测是「环境敏感型」评测：同一模型同一指令，在不同的推荐流、不同的登录态、不同的弹窗广告下，会产生不同轨迹与不同成败。这种噪声会直接污染三类科研判断：(a) 模型间排序（排行榜不可复现，A 比 B 好可能只是运气）；(b) 消融与训练改进的归因（改进被环境方差淹没）；(c) 失败模式分析（无法判断失败是能力不足还是环境扰动）。

3) 已有方案的两条路径与其隐含假设（部分为合理推断/推测）。
- 简化环境路径：假设「交互逻辑可抽象」，换取可控性与低成本；代价是分布外，真实 App 的视觉密度、层级结构、异步加载、复杂导航被抹去，导致结论向真实部署迁移时打折。
- 真实商业 App 路径：假设「真实即有效」，换取生态效度；代价是环境非平稳，且部分 App 内容依赖账号与地域，第三方无法复现同一条件。
- 论文选择的第三条路径隐含一个关键假设：对 Agent 能力评测而言，真正决定成败的是「与任务相关的交互逻辑 + 可确定性判定的结果状态」，而不仅是像素视觉保真；即可以用「按维度近似」的现实性（reproduce the visual appearance, in-page interaction...，来自 Limitations 片段）替代整体性真实。这个假设本身是本论文最需要被外部检验的地方，因为它决定了基准结论能否外推到真实商业 App。

4) 判据设计上的难点（合理推断）。要让「结果导向验证」成立，任务结果必须能被机器确定性地判定；这要求后端数据可控（同一初始状态、同一后台数据），也要求任务的正确性定义明确（例如目标字段被正确写入、页面状态达到某固定条件）。这样做的代价是任务形态天然偏向「有明确终态」的操作，而对开放式、主观性、需要真实网络副作用的任务覆盖有限。

5) 从评测范式看问题的性质。本文属于「环境构造型贡献」：它不提出新 Agent 架构，而是把「评测环境」当作一等研究对象，主张环境的可控性是可复现科学比较的前提。与之竞争的路子包括：在真实 App 上多轮重复采样取平均、用录制的确定性回放（cassette/replay）、用真实 App 但冻结后端快照、以及用合成任务在模拟器上做规模化自动生成。本文站在「模拟 App + 确定性后端」这一侧，并额外用 coding-agent 辅助构建来压低模拟环境的人力成本——这正是它声称「通用且高效」的来源（合理推断）。

Q3: 论文如何解决这个问题？

论文的解法可以拆成「环境构造」「任务构造」「判定机制」「评测协议」四个层面。

1) 可控模拟 App（核心机制，明确支持）。不直接在真实商业 App 上评测，也不退回到简化 App，而是构造保留「与任务相关的交互逻辑」的模拟 App，同时让评测具备确定性。这样做的逻辑是：决定任务成败的是交互逻辑与状态转移，而非推荐流、广告与账号个性化。控制变量后，同一模型多次运行的差异可归因于模型而非环境。

2) 可控后端数据 + 结果导向验证（明确支持）。摘要与 Conclusion 片段指出，可控后端数据与确定性（deterministic）的结果验证共同移除了主要的环境随机性来源，从而使跨模型比较可复现。这意味着判定不依赖轨迹匹配（不要求走同一条路径），而是检查最终状态/结果是否正确——这既容忍了合理的多解路径，又让判分可机器化。

3) 构建流程：coding-agent 辅助 + 人工核验（明确支持）。Introduction 片段描述为：编码 agent 在约束下生成候选实现，随后由人类开发者检查、实际运行并迭代修正，之后才用于评测。论文自陈该流程「减少了重复实现成本」，即它同时是「通用性和效率」主张的工程支点。需要注意：证据显示该流程的成本效益是作者陈述，检索片段中未见量化的工时或缺陷率数据（信息缺口）。

4) 数据与任务覆盖（明确支持）。557 个任务，17 个高频中英文 App。检索片段未给出任务类型分布、每个 App 的任务条数、难度分层定义（信息缺口）。

5) 评测协议：19 个 GUI Agent，通用与 GUI 专用两类，同一环境与同一任务集下横向比较；报告完成率与「无任何 agent 解决」的任务比例。

6) 现实性的近似策略（来自 Limitations，明确支持但为论文自述的边界）。现实性按维度近似：视觉外观、页内交互等在检索片段中被提到被复现，但不是整体照搬真实 App。行为保真度是间接测量的（通过附录 E 的 placeholder residual），而不是直接给出「已实现交互元素覆盖率」这样的指标。这说明模拟 App 的完整性验证手段本身是本文方法链条中最弱的一环。

7) 设计上的权衡（合理推断）。把后端做可控，意味着必须放弃真实网络副作用（支付、真实消息发送、真实第三方同步），也就自然地留下跨 App 工作流、实时交互、无障碍场景、安全敏感场景四类未覆盖面（Limitations 明确列为未来扩展方向）。

Q5: 发现了什么实验现象？

从检索片段可提取的实验现象，及其张力与反直觉处如下。

1) 能力上限远低于「已解决」：19 个 agent、含通用与 GUI 专用系统，最好者也只有 50.27%。这条现象的意义在于它发生在受控环境里——排除了广告、推荐、账号噪声后依然半数失败，说明瓶颈主要落在 agent 自身能力（长流程规划、数值推理、动作效率），而非环境不可复现（合理推断，但需要与真实 App 基准的分数做可比对照才能确证）。

2) 存在相当规模的「集体盲区」：28.55% 任务无任何 agent 完成。这是一个容易被忽略的负面结果类型——它把「模型间差异」问题转化为「任务集上限」问题。研究者需要区分两种解释：(a) 任务超出当前能力；(b) 任务在模拟环境中实际不可达或期望终态定义有歧义。检索片段未提供这类任务的分类或人工复核结论，属信息缺口。

3) 失败与流程长度的相关性：失败集中在更长的 workflow。这符合长 horizon 任务的通用经验，但在本基准中的具体形态（第几步开始退化、是否出现重复动作循环、是否有上下文截断）在片段中未展开。

4) 数值推理是独立失败源：数值推理任务被单列为失败集中区。这暗示视觉-语言模型式的 agent 在需要读取、比较、计算页面数字（金额、数量、时间、比率）时系统性易错；这类失败在纯操作类任务中不会显现，属于任务类型分层后才能暴露的现象。

5) 效率与成功率分离：失败轨迹被「高动作开销 + 预算耗尽」标记。这是一个重要的评价设计张力——同一个任务既可因「做错」失败，也可因「绕远路直到预算用尽」失败。这意味着仅报告成功率会低估效率维度的模型差异；也意味着预算设置本身会直接塑造排行榜（推测：预算越紧，效率差异越被放大）。

6) 反直觉点（相对「真实环境更难、模拟环境更容易」的直觉）：本文的 50.27% 并不显得比真实环境下的常见报告更宽松，提示「简化环境→分数虚高」这一担忧在本基准的模拟 App 上未必成立；但检索片段中没有与真实 App 基准的并列对照表，这一判断只能作为待验证推测。

7) 消融趋势、scaling trend 与负结果：检索片段未包含消融实验（如动作空间、观察模态、是否给 OCR/可访问性树、是否允许重试）与规模趋势（模型规模 vs 成功率）的数据。这是一处明显缺口：对于「可复现评测」类论文，最应展示的恰恰是同一模型重复运行的方差与不同运行配置的敏感性。

Q6: 有什么可以进一步探索的点？

论文自身在 Limitations 中明确指出的扩展方向（明确支持）：跨 App 的工作流（cross-app workflows）、实时交互（real-time interaction）、面向无障碍的任务（accessibility-oriented tasks）、安全敏感场景（security-sensitive scenarios）。这四条实际上对应四类当前被排除的复杂因子，每一条都会重新引入一部分不可控性，因此在扩展时需同步重新设计确定性验证手段。

由本文设计与证据缺口可合理推出的可探索方向：
1) 保真度度量的正式化。现状是行为保真度通过附录 E 的 placeholder residual 间接测量，而非「已实现交互元素覆盖率」这类直接指标。可以构建一套分层保真度协议：视觉层（截图/布局相似度）、结构层（UI 树、可达性属性）、逻辑层（状态转移与错误处理路径覆盖率）、数据层（后端一致性）。
2) 模拟 App 与真实 App 的一致性验证。选取若干真实 App 做同任务双环境对照，量化「模拟环境分数 → 真实环境分数」的迁移损失，从而界定结论可外推的范围。这是本文结论效度的关键缺口。
3) 可复现性本身的度量。既然核心卖点是可复现，应报告同一模型重复运行的分数方差、轨迹方差、以及环境初始化是否完全确定（例如是否存在时间戳、随机 ID、异步渲染抖动）。
4) 预算与效率作为一等指标。把「动作开销 / 预算耗尽率 / 达到目标的步数分布」做成与成功率并列的报告项，并研究预算敏感性曲线，避免排行榜被单一预算值支配。
5) 失败归因分类学。对 28.55% 的零通过任务做人工分类（能力不足 vs 期望态歧义 vs 路径不可达），形成可复用的诊断标签体系。
6) 任务生成的自动化与质量控制。当前的 coding-agent 辅助 + 人工核验流程可从「效率声明」升级为「可测量流水线」：报告缺陷率、返工次数、单位任务成本，并探索自动质量门（例如状态可达性证明、任务可解性验证）。
7) 任务维度扩展。数值推理是已识别的强失败点，可专门构建难度阶梯化的数值子集；长流程可构建步数递增的 scaling 序列，以刻画能力拐点。
8) 动态与多用户因素。把内容变化、并发用户、账号状态这些被刻意剔除的变量以「受控注入」的方式重新引入（可控噪声），从而研究噪声鲁棒性与可控性之间的连续谱，而不是二值取舍。
9) 与相邻领域的迁移：可控模拟环境 + 确定性判定的范式可推广到桌面 GUI、Web agent、以及需要长程状态维护的软件工程 agent 评测；反向地，可借鉴软件测试中的 flaky test 治理、record-replay 与 hermetic environment 实践来强化可复现主张（跨领域联系，属推测性建议）。

Q7: 总结一下论文的主要内容

本文是一篇以「评测环境」为核心贡献的基准类论文，主线是：移动 GUI Agent 评测长期在「真实」和「可复现」之间被迫二选一，作者主张用可控模拟 App 把两者同时拿下，并以此基准对当前 agent 能力做出一个「远未解决」的判断。

【问题主线】
论文开篇即指出，移动 GUI Agent 能按自然语言指令执行任务，但评测要同时真实且可复现很难。已有基准分两类：简化 App 缺少真实移动端的复杂度；真实商业 App 则引入推荐、广告、账号与内容变化等不受控变异。作者承认既有工作（Zhang et al., 2024a）已指出可复现性问题，但认为通用且高效的解决方案仍然缺失——这构成了本文的问题空间。

【方法主线】
1) 环境哲学：不去复制真实 App 的全部，而是复制「与任务相关的交互逻辑」，并让后端数据可控，从而获得确定性。
2) 判定机制：以结果导向（outcome-based）的确定性验证取代轨迹匹配，使多解路径都被接受，同时让判分机器化、可重复。
3) 构建流程：coding-agent 在约束下生成候选 App 实现，人类开发者检查、运行、迭代修正，再投入评测。作者将这一流程视为「通用且高效」的具体落地方式，即压低模拟环境的人力成本。
4) 规模与覆盖面：557 个任务，17 个高频中英文 App。
5) 现实性的处理方式：按维度近似（视觉外观、页内交互等被复现），而不是整体照搬（此点来自 Limitations）。

【实验主线】
作者在统一环境与统一任务集下评测 19 个 GUI Agent，涵盖通用系统与 GUI 专用系统两类，做跨模型可复现比较。主结论有三条：最好的模型只完成 50.27% 的任务；28.55% 的任务没有任何 agent 能完成；失败集中在更长的流程、数值推理任务，以及由高动作开销与预算耗尽标记的低效轨迹。

【论证逻辑上的关键节点与张力】
- 论文的核心论证是「控制环境噪声 ⇒ 跨模型比较可信 ⇒ 得到的结论（能力远未解决）反映的是能力而非环境」。这个链条中，环境保真度是本论文自认的弱点：Limitations 明确说现实性是逐维度近似、行为保真度通过附录 E 的 placeholder residual 间接衡量，而非直接给出已实现交互元素的覆盖率。
- 「结果导向验证」保证判分可复现，但也把基准偏向有明确终态的任务形态；跨 App 工作流、实时交互、无障碍任务、安全敏感场景被明确列为未覆盖方向。
- 28.55% 的零通过任务是一把双刃剑：既是有力的「能力不足」证据，也需要排除任务不可达或期望终态歧义的可能性；检索片段中未见对这批任务的人工复核结论。
- 效率维度（动作开销、预算耗尽）与成功率耦合，提示单一成功率指标可能低估模型间差异，也提示预算设定会塑造排行榜。

【总体定位】
这是一篇「基础设施/评测范式」型论文，而非新的 Agent 架构论文。它的价值主张是：可复现的受控评测能够给出稳定、可比较、可复算的能力画像，并暴露具体瓶颈（长流程、数值推理、动作效率）。它的主要风险在于外部效度——模拟环境与现实 App 之间的迁移损失尚未被量化。
